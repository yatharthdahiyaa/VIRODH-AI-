# threat-guard (Virodh AI) — architecture map

_Generated by **Understand-Anything** (`/understand` pipeline) from the threat-guard codebase. Open the interactive graph with `open-dashboard.ps1`._

Virodh AI / Threat Guard: an explainable, model-agnostic security and governance gateway in front of vision-language models that inspects every prompt and image (OCR, QR, decoders, injection/harm/cross-modal classifiers, adversarial-noise engine), applies per-key policies and operator rules, forwards only allowed requests through an OpenAI-compatible proxy, checks replies, and logs decisions; with a React + Node.js dashboard and an evaluation harness built on OmniSafeBench-MM.

Scope: our code only (Threat Guard engine, Virodh gateway, dashboards, plugins, evaluation, tests, config, deploy, docs). Upstream OmniSafeBench-MM code, datasets and generated outputs are excluded (see `.understandignore`).

## Guided tour

**1. Project Overview** — Virodh AI is an OpenAI-compatible security gateway for vision-language models, built on the Threat Guard inspection engine. Every prompt and image is inspected, decided by the API key's policy, forwarded only if allowed, re-checked on the way back, and logged, with every ALLOW / REVIEW / BLOCK decision backed by evidence. The README, the gateway design doc, and the threat model set out the stages (ingress, extract, detect, fuse, policy) that the rest of this tour follows.
  Files: `README.md`, `docs/VIRODH_GATEWAY.md`, `docs/threat_model.md`

**2. Gateway Entry Point** — virodh/server.py is the FastAPI application that wires the public gateway, the admin API, the website/console pages, and the legacy Threat Guard routes into one process. Its runtime limits (body and image size, scan concurrency, queueing, timeouts, cache) come from config/virodh.yaml through virodh/config.py, which adds typed environment-variable overrides. tg_bootstrap.py runs at import time to load .env secrets and patch the upstream OmniSafeBench-MM config loader, so the guard and benchmark code share one setup.
  Files: `virodh/server.py`, `virodh/config.py`, `config/virodh.yaml`, `tg_bootstrap.py`

**3. How Clients Call It** — Clients point any OpenAI SDK at /v1 with a Virodh key. gateway.py is the public Chat Completions API: it authenticates the key, has the request inspected, applies the policy, forwards it upstream, and records the result. openai_compat.py turns the OpenAI wire format into "inspection units" (text and images) and builds compatible responses, including the blocked ones. security.py handles API-key extraction and access control for the admin console.
  Files: `virodh/gateway.py`, `virodh/openai_compat.py`, `virodh/security.py`

**4. Core Schemas and Orchestration** — guard/schemas.py has the highest fan-in in the codebase. It defines the shared vocabulary: the Decision and Trust enums, TextSegment, DetectorResult, and ScanReport. guard/engine.py is the ThreatGuard orchestrator that runs ingress, extraction, the hosted classifiers, the detectors, fusion, and policy in order, using thresholds from config/guard.yaml. On the gateway side, virodh/inspector.py sends each inspection unit from Step 3 through this engine with bounded concurrency.
  Files: `guard/schemas.py`, `guard/engine.py`, `virodh/inspector.py`, `config/guard.yaml`

**5. Ingress and Visual Extraction** — Before anything is analysed, ingress.py enforces size, type, and pixel limits, re-encodes images to strip metadata, and hashes them with SHA-256. The extraction pipeline then reads the image the way an attacker hopes only the model will: QR codes at full resolution, OCR with RapidOCR on the CPU, orientation recovery for mirrored or rotated text, faint-text passes, and decoders for base64, reversed text, ROT13, and word substitutions. The output is a set of untrusted text segments that the detectors work on.
  Files: `guard/ingress.py`, `guard/extract/pipeline.py`, `guard/extract/ocr.py`, `guard/extract/qr.py`, `guard/extract/decoders.py`

**6. Threat Detectors** — Each detector implements the shared Detector interface from base.py and receives an AnalysisContext built from the extracted segments. The injection detector combines AI-directed regex patterns with Prompt Guard scores, the harm detector converts policy-classifier verdicts into evidence, and the obfuscation detector deterministically flags hidden-text signals such as low contrast, mirroring, and encodings. The composite detector classifies prompt and image text together to catch attacks that are split across modalities.
  Files: `guard/detectors/base.py`, `guard/detectors/injection.py`, `guard/detectors/harm.py`, `guard/detectors/obfuscation.py`, `guard/detectors/composite.py`

**7. Risk Fusion and Policy** — fusion.py merges the detector outputs from Step 6 into one risk score using max and noisy-OR, then amplifies risk when obfuscation is present. policy.py maps that fused risk to ALLOW, REVIEW, or BLOCK. Its profiles can only make decisions stricter, and fail-safe rules apply when classifiers are unavailable. guard/llm.py provides the cached clients for the hosted classifiers (Llama Prompt Guard and policy models over OpenAI-compatible APIs) that feed the detectors.
  Files: `guard/fusion.py`, `guard/policy.py`, `guard/llm.py`

**8. Forwarding and Output Guard** — Allowed requests are wrapped in a trust-separating envelope (envelope.py) that labels image content as untrusted data before the model sees it. upstream.py forwards them through a pooled async HTTP client, with a circuit breaker per upstream and an offline mock model. When the reply comes back, output_guard.py checks it for markers that appeared only in untrusted image text, so the gateway can tell a hijacked answer from a genuine one.
  Files: `virodh/upstream.py`, `guard/envelope.py`, `guard/output_guard.py`

**9. Operator Policies and Storage** — Operators control the gateway with per-key policy profiles (virodh/policy.py, Pydantic models) that decide how to act on guard decisions and which topics to deny. topics.py enforces denied topics by sending the request to the guard's classifier chain as untrusted data. store.py keeps hashed API keys, policies, request logs, rate-limit windows, and usage totals in SQLite. admin.py exposes them through the /admin/api router, and metrics.py publishes Prometheus counters and histograms.
  Files: `virodh/policy.py`, `virodh/topics.py`, `virodh/store.py`, `virodh/admin.py`, `virodh/metrics.py`

**10. Dashboard Node Backend** — The React dashboard is served by an Express backend that owns human accounts, separate from the gateway's API keys. index.js sets security headers, the CSP, and CSRF origin checks. auth.js does scrypt password hashing and session tokens. db.js stores users and sessions with Node's built-in node:sqlite in WAL mode. proxy.js streams requests through to the Python Virodh engine from Steps 2-9, so the dashboard never reimplements inspection.
  Files: `server/src/index.js`, `server/src/auth.js`, `server/src/db.js`, `server/src/proxy.js`

**11. React Dashboard** — main.jsx mounts the React SPA with BrowserRouter and AuthProvider and declares the public and authenticated routes. api.js is the same-origin fetch client for the Node backend from Step 10, and ui.jsx is the shared library of UI components (chips, panels, tables, drawers, toasts). Layout.jsx is the authenticated shell, grouped into Build, Govern, and Admin sections. Pages such as Policies.jsx give operators an editor for the policy profiles introduced in Step 9.
  Files: `web/src/main.jsx`, `web/src/api.js`, `web/src/ui.jsx`, `web/src/pages/app/Layout.jsx`, `web/src/pages/app/Policies.jsx`

**12. Adversarial Image Engine** — Not every attack hides text: some images carry adversarial pixel perturbations instead. This second engine combines a local ResNet18 classifier's predictions, four detectors (statistical, frequency, feature-squeezing consistency, and local-region outliers), and an optional learned model into one risk score. learned.py computes the shared feature vector used in both evaluation and production, and the calibration JSON stores clean-image percentiles so features are normalised the same way everywhere.
  Files: `guard/adversarial/engine.py`, `guard/adversarial/detectors.py`, `guard/adversarial/learned.py`, `guard/adversarial/classifier.py`, `config/adversarial_calibration.json`

**13. Research API and Benchmark Plugins** — Before the Virodh product existed, Threat Guard was exposed through a research FastAPI app (app/main.py) with scan, system, adversarial, and evaluate routes, backed by a lazily built ThreatGuard singleton in services.py. The tg_plugins package connects the engine to the upstream OmniSafeBench-MM toolbox. The threat_guard defense plugin forwards only ALLOW decisions, and the canary attack plugin generates harmless hijack images, with every plugin registered in config/plugins.yaml.
  Files: `app/main.py`, `app/services.py`, `tg_plugins/defenses/threat_guard.py`, `tg_plugins/attacks/canary.py`, `config/plugins.yaml`

**14. Evaluation and Testing** — calibrate.py picks the REVIEW and BLOCK thresholds on the validation split only, using a Youden-style sweep. metrics.py combines guard decisions, guarded and unguarded replies, and judge verdicts on the test split. virodh_e2e.py exercises a running gateway through the official OpenAI SDK. The pytest suites cover extraction of hidden text, fusion, policy, and the gateway end to end, using fake engines and mocked hosted classifiers so they run without network access.
  Files: `eval/calibrate.py`, `eval/metrics.py`, `eval/virodh_e2e.py`, `tests/test_guard.py`, `tests/test_virodh.py`

**15. Deployment and Scaling** — For local development, start_virodh.ps1 builds the React app, starts the Python engine on port 8000, and starts the Node dashboard on port 3000. In production, the CPU-only Dockerfile packages the gateway on python:3.11-slim, and docker-compose puts an nginx TLS/load-balancer in front of stateless gateway replicas that can be scaled out. virodh.conf routes requests with least-connections balancing and per-IP rate limits.
  Files: `deploy/docker-compose.yml`, `deploy/Dockerfile`, `deploy/nginx/virodh.conf`, `start_virodh.ps1`
